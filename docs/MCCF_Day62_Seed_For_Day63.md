## Major Debugging Arc — Orbit Implementation (the bulk of today's session)

This took most of the session and surfaced genuinely valuable, durable X_ITE API knowledge — now captured in spec v1.3 §4. Summary of the sequence for anyone picking this up:

1. **First attempt:** keyframes computed, written via fabricated `new X3D.MFFloat(...)` / `MFVec3f(...)` bulk constructors. Silently did nothing — no error, camera snapped to start and froze.
2. **ROUTE toField naming confusion:** tried `translation`/`rotation` (matching the bare field table), then `set_translation`/`set_rotation` (matching the official tutorial's worked example) — the latter is correct, confirmed.
3. **Diagnostic instrumentation itself became a bug:** first diagnostic attempt used fabricated `addFieldInterest` API (doesn't exist). Second attempt used `addFieldCallback` correctly but called a nonexistent `.getValue()` on the callback value, throwing an uncaught exception **inside X_ITE's own synchronous event dispatch** — this stalled the avatar's walk animation entirely, a real production-grade lesson about diagnostic code safety, not just a logging bug.
4. **Root cause, finally isolated cleanly:** `canvas.browser.currentTime` returns `0` in this X_ITE build (11.6.0). Every other `startTime` write in the codebase already guards against this with a `performance.now()/1000` fallback — the orbit code was the one call site that didn't. `startTime=0` → `fraction_changed` evaluates to `NaN` forever → interpolator always returns keyframe 0 → camera looks frozen despite every other part of the chain (keyframes, ROUTEs, TimeSensor activity) being completely correct.
5. **Fixed, confirmed working** in live playback.
6. **Author's structural insight mid-session:** rather than computing the orbit around the subject's world position every frame (tracking), simply reparent the orbit Viewpoint inside the avatar's own Transform (same pattern as Eye/Side) so the avatar's motion is inherited for free via ordinary scene-graph semantics. This is architecturally superior and is now `agent_orbit`, confirmed working, distinct from the original free/world-space `orbit`.

**Takeaway for future sessions:** when a camera/Transform-driving feature "moves once then freezes," suspect the timer's `startTime`/`enabled` handshake before suspecting ROUTEs or keyframes — in this codebase, `currentTime=0` is a known trap.

## Key Architecture Facts (carry forward)

### Free orbit vs agent_orbit — never conflate
- Free `orbit` (Camera Moves group): circles a **fixed world point**, computed once at cue-fire time from `_resolveSubjectPos`. Does not follow a moving subject. Uses singular `CAM_Timer`/`CAM_PosInterp`/`CAM_OriInterp`/`CAM_Free_Transform`.
- `agent_orbit` (Agent POV group): circles the **avatar's current position continuously**, because it's parented inside the avatar's Transform. Follows the avatar if it moves. Uses per-agent `CAM_OrbitTimer_{name}`/`CAM_OrbitPosInterp_{name}`/`CAM_OrbitOriInterp_{name}`/`CAM_OrbitXform_{name}`.
- Both confirmed working independently. Do not merge their code paths — they solve genuinely different problems.

### X_ITE SAI corrections (full detail in spec v1.3 §4 — summary here)
- `canvas.browser.currentTime` returns 0 in this build. Always fallback to `performance.now()/1000`.
- TimeSensor/Transform scalar fields: direct property assignment (`node.enabled = true`), not `getField().setValue()`.
- MF (multi-value) fields: indexed assignment (`field[i] = value`, `field.length = 0` to clear), never bulk constructors like `new X3D.MFFloat(...)` — these don't exist.
- ROUTE targets into Transform `translation`/`rotation`: use `set_translation`/`set_rotation` prefix, despite the bare field table not listing it.
- `Browser.addRoute(src, srcField, dst, dstField)` is real and documented — useful as a defensive runtime assertion alongside static XML ROUTEs.
- `addFieldCallback(key, fieldName, callback)` is the correct live-value listener API. `addFieldInterest` does not exist. Callback body must self-protect with try/catch — X_ITE invokes it synchronously inside its own event loop, and an uncaught exception there can stall unrelated scene state (confirmed: froze avatar walk animation).
- Stale callback keys: `addFieldCallback` silently no-ops if the same key is reused on the same node/field. Relevant for any cue that can fire more than once per session.

### Parenting beats tracking — general principle, not just for orbit
If a shot needs to follow a moving subject indefinitely, parent the camera Viewpoint inside the subject's own Transform (same pattern as `VP_{name}_Eye`). Never compute the subject's world position every frame from JS. This is now the confirmed, preferred architecture for any future "follow the avatar" camera work — see `track` in the deferred list below.

### Character Creator decision — held, not implemented
Considered extending the agent-attached pattern to `over_shoulder`/`profile`, with `two_shot` becoming an over-the-shoulder variant aimed at a second subject. Two paths: (a) Composer-baked generic defaults for every avatar, same as Eye/Side/Orbit today, or (b) Character Creator-authored per-avatar, treating camera shots as an avatar-asset-tier concern parallel to behavior clips (idle/walk/run/kick).

**Decision: held for testing before implementation.** Option (b) is architecturally preferred but needs UI scoping work not yet done. Do not implement (a) as a stopgap — it would create a second migration later. Full reasoning in spec v1.3 §3b.
