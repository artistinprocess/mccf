MCCF V5 Systems Implementation

Oct 24, 2026 · MCCF Product Team

This document describes how the V5 code is built, module by module, and records the defects found while checking each module against the User's Guide. It is written from the source files, not from memory. Where a claim could not be checked, it says so. Section ids (IMPL-nn) are stable so the sections can move into the CSDB later.

1. System map (IMPL-01)

MCCF is a localhost system. A Flask server (mccf_api.py, about 3,300 lines) serves the static tools and the APIs. The tools are single HTML files served from the static folder, for example localhost:5000/static/mccf_x3d_loader.html.

Part File Role
Server mccf_api.py Flask app. Scene and zone save, arc runner, scene parsing, registers the blueprints below.
Coherence engine mccf_core.py ChannelVector, CoherenceRecord, Agent, CoherenceField, MetaState, Identity. A pure computation module that holds its state in memory. For each pair of agents it tracks how coherent each feels toward the other, and for each agent its drift, regulation and mode. Callers pass in channel vectors and read back results. It does no file or network I/O: the API modules do that.
Voice API mccf_voice_api.py Blueprint voice_bp: /voice/speak, /voice/preview, /voice/configure, /voice/state, /voice/prosody, /voice/adapters, /voice/lexicon and /voice/lexicon/reload.
Zone API mccf_zone_api.py Blueprint zone_bp: /zone (list, create), /zone/<name> (read, delete), /zone/<name>/episode, /zone/presets, /scene/pressure, /waypoint, /path, /path/<name>/arc, /scene, /export/x3d/zones and /sensor/spatial. The scene graph lives in memory only and is empty after a restart. The host application must attach zone_bp.scene and zone_bp.field after registering the blueprint.
LLM adapters mccf_llm.py Adapter registry (registered: stub and ollama; hosted adapters exist in the code but are not registered), affective prompt builder, voice parameter mapping.
Cultivars mccf_cultivar_lambda.py Blueprint cultivar_bp: CultivarDefinition, CultivarRegistry, /cultivars endpoints.
H-Anim mccf_hanim_api.py Blueprint hanim_bp: avatar upload, preview, list, H-Anim export, joints, displacers, ingest (about 4,100 lines).
Tools Launcher, Dashboard, Scene Composer, Character Creator, X3D Loader, Dialogue Editor, Events Editor, Route Graph, Ambient Composer, Help Composer (the lesson player) Browser tools, one HTML file each.

Not yet reviewed: mccf_cultivars.py (the built-in cultivar dictionary) and any server routes the Events Editor and Route Graph use.

2. XML documents and namespaces (IMPL-02)

The schema (Appendix B, version 1.1) puts every document type in the namespace http://mccf.artistinprocess.com/v1.

Document Written by Read by Namespace today
Scene XML Composer, _doExportSceneXML Server scene parser, Loader, Composer, Events Editor v1 (added in V5)
Zone XML (ZoneSet) Composer, exportZoneXML, saved through /scene/save/zones Composer, Loader v1 (added in V5)
Take (arc export) Server, arc export Server cultivar loader (reads the Cultivar element) none; must stay none
Cultivar CultivarDefinition.to_xml CultivarRegistry, hanim export cultivar/v3 (differs from the schema, see IMPL-I03)
ZoneTemplate Composer Server, /zones templates none; must stay none

Reader rules. The server's scene parsers remove xmlns before parsing (mccf_api.py around lines 746 and 2372). The cultivar reader uses the {*} wildcard, so it accepts any namespace. Browser readers use querySelector and getElementsByTagName, which ignore a default namespace. The zone-template reader and the cultivar and take loaders use ElementTree without stripping, so those files must not gain a namespace.

Element name. The per-agent element in a scene is AgentPlacement. EmotionalArc now means only the take root. The Composer writes the new name. The Composer, the Loader and the server read both, so older scenes still open (IMPL-I08). The schema keeps EmotionalArc as a deprecated alias inside a Scene until old scenes are re-saved.

3. Voice and dialogue (IMPL-03)

Preview pipeline (POST /voice/preview, stateless, no agent, no LLM call):

  1. Count positive, negative and uncertainty words in the text from module-level word sets.

  2. Compute tag valence. It needs at least two positive or negative hits, otherwise it is 0.0. Uncertainty words weigh 0.15.

  3. Count channel words (S, E, P, B) and derive arousal (0.3 + 0.6 times min(1, hits/8)) and engagement from the S and E hits.

  4. derive_emotion_tag turns valence, arousal and engagement into one of the 11 core tags, or none. The tag cute is never derived: the rules cannot tell it from the other positive tags using valence, arousal and engagement alone, so it appears only when the author types it.

  5. Return suggested_tag and suggested_tts_text, which is the tag in brackets followed by the text.

Speak pipeline (POST /voice/speak, server-sent events): builds the affective context from the field, sends the affect parameters first, streams tokens from the selected adapter, records the response sentiment into the field, and ends with a done event.

Tags. The 22 delivery tags are hardcoded in the Dialogue Editor (11 core and 11 nonverbal). Free-form tags in a line's ttsText are accepted.

Lexicon packs. Packs are JSON files read at start-up from lexicon_packs/ beside mccf_voice_api.py (POST /voice/lexicon/reload re-reads them; a broken file is logged and skipped). A word pack (default_narrative) adds pos, neg, unc and S, E, P, B words on top of the core lists. An engine pack (elevenlabs_v3) supplies the delivery tag chips in groups, with an optional tag_map from the decision tree's tag to the engine's tag. With no pack active, scoring is identical to the core lists. GET /voice/lexicon lists the packs; /voice/configure and /voice/preview accept lexicon_packs and engine_pack. The core lexicon itself is still in code (IMPL-I01).

4. LLM adapters (IMPL-04)

All adapters implement complete() as an async generator. The registry holds stub, anthropic, openai, ollama and google. The prompt builder turns the field state into narrative text: arousal, valence, regulation, relationships, zone pressure, trajectory and a coherence-health block.

  • Ollama is the only supported adapter in this release. It posts to /api/chat on localhost:11434 with stream set to false, waits 180 seconds, retries once at 240, then yields the whole reply word by word.

  • Hosted adapters (anthropic, openai, google) are still registered and still accepted by /voice/configure. Hiding them in the UI does not remove them (IMPL-I02).

  • API key. /voice/configure keeps the key in process memory (_voice_state). The /voice/state and /voice/configure responses do not return it. Other modules were not checked for logging.

5. Cultivars and characters (IMPL-05)

A CultivarDefinition holds weights, regulation, shadow context (lambda), voice, alias, portrait, H-Anim figure, receptivity and a behavior-clip table. CultivarRegistry loads the built-in dictionary, then every .xml file in cultivars/. The registry key is the name attribute, not the filename.

  • The writer's element order matches the schema.

  • Files are saved as cultivars/cultivar_<lowercase name>.xml. The H-Anim exporter uses the same slug so that both write one file.

  • The writer does not escape text (IMPL-I04) and the loader skips a malformed file without a message (IMPL-I04).

6. H-Anim API (IMPL-06)

Routes: /avatar/upload, /avatar/preview, /avatar/list, /hanim/skin_upload, /hanim/export, /hanim/joints, /hanim/wire-joints, /hanim/normalize-joints, /hanim/build-displacers, /hanim/ingest, /hanim/ingest-mixamo. The export writes the avatar X3D, an expressions XML file, a camera-rig manifest and the cultivar's clip data. Every write keeps five timestamped backups of the file, and a single avatar file can be about 24 MB. Reviewed so far: route list, file paths and the cultivar namespace constant. The export logic itself is not yet reviewed.

7. Coherence engine (IMPL-07)

The engine is a pure computation module. It imports only math, time, uuid, random, collections and dataclasses, and it never reads a file, opens a socket or calls a service. All its state lives in memory, and it does its work when called: callers pass in channel vectors and read back coherence scores, affect values and reports. Everything that touches the outside world (files, HTTP, the browser, the voice engine) lives in mccf_api.py and the other API modules. Coherence is directional: what A feels toward B differs from what B feels toward A. Each record keeps a rolling history of 20 episodes with exponential decay, a credibility score that drops when a channel is implausibly steady, and a coupling-strength modulation (CCS). An Agent also carries MetaState, Identity (drift capped at 0.10) and a mode (explore, exploit, repair, avoid or shift). CoherenceField, Librarian and Gardener provide the matrix, the reports and the interventions. The voice API feeds it through field.interact().

8. Route Graph and effects

The Route Graph is a node-and-wire editor, embedded as a Composer tab (mccf_route_graph_prototype.html). A node is an X3D node and a wire is a ROUTE. An author wires sensors to interpolators to targets without writing X3D.

Node types. Transform, ProximitySensor, TimeSensor, ScalarInterpolator, ColorInterpolator, PositionInterpolator, OrientationInterpolator, RecordedPath, BasicPointLight, BasicSpotLight, BasicDirectionalLight, TimelineTrigger, BasicAudioSource and TouchSensor. Script nodes are registered on import from a scene, with their fields read from the Script itself. Only a TimeSensor and the four interpolators can be created fresh. Every other type is a reference to something that already exists in the scene, such as an agent's Transform or a placed light.

Persistence. The tool sends its state to the Composer as a mccf_route_graph_save message: nodes, connections, hidden layers and nodes, and the schema of any Script type used. The Composer keeps it, sends it back when the tab reopens, and writes it into scene.xml as a RouteGraph element whose data attribute holds the JSON.

Export rules. At export the Composer bakes the graph into the compiled X3D under two hard rules. It never creates a node whose DEF already exists anywhere in the scene being built, and it never repeats a ROUTE that already exists. Both checks scan the export text built so far, so they reflect the real scene. Nodes the event cues generate themselves (names beginning Path, PathEase, Turn or Effect, then Timer, Interp or Orient, then EC) are skipped, because only the cue builders make correct ones.

Effect assets. Click a wire, and the whole connected chain it belongs to can be saved as an Effect Asset: an X3D 4.1 Interchange file holding the nodes and their ROUTEs. Nodes outside the chain are written as comments, so reusing the file needs a node with the same DEF in the target scene. The tool downloads the file and also posts it to /effects/save, which writes only to the user tier. The library has three tiers under static/x3d/Effects/: rich (ports of official X_ITE reference examples), common (simpler versions) and user (live saves). Load Effect Asset lists a tier with /effects/list and merges the chosen file into the graph through the same parser as scene import.

Not built. Shift-click subassemblies (naming and seeding are undecided). Load Effect Asset asks for the tier and the file name through browser prompt boxes instead of a list (IMPL-I17).

9. Assets and libraries

Every library is a folder under static/x3d/ that the server lists and the Composer reads. MCCF does no X3D schema validation on what goes in. X_ITE checks a file when it loads it, so a bad asset fails at that point.

Library Folder Listing Accepts Notes
Assets X3DAssets/ GET /x3d/assets/list .x3d, .glb, .gltf Top level only. The texture/ subfolder is not listed. glTF is preferred for static objects: fewer vertices.
Audio and MIDI X3DAssets/media/ GET /media/list (subdir, ext) mp3, wav, ogg, flac, aac, m4a, mid, midi subdir=convolver gives X3DAssets/media/convolver/file.wav.
Effects Effects/rich, common, user GET /effects/list?subdir= .x3d Live saves write only to user.
Compiled scenes static/x3d/ GET /scene/x3d/list .x3d POST /scene/x3d/upload writes {scene_name}.x3d.
Scene definitions scenes folder GET /scene/list/scenes .xml POST /scene/save/scene and /scene/save/zones write them.
Cultivars cultivars/ cultivar registry .xml File name cultivar_<slug>.xml (IMPL-I10).
Lexicon packs lexicon_packs/ GET /voice/lexicon .json See section 3.

Placing an asset. The Composer writes a placed asset as a Transform (DEF PlacedAsset_name, with translation, rotation and scale) holding an Inline (DEF AssetInline_name, with the asset's url). A click on the map places it. It can then be dragged or adjusted with the X, Y and Z inputs.

Editing an asset. POST /x3d/assets/save overwrites an existing asset file. Only .x3d files can be edited as text. The server resolves the real path and refuses anything that escapes X3DAssets/. The Events Editor's asset-file viewer uses it.

Extending the libraries. Sunrize and X_ITE can author or convert assets. A file dropped into the folder appears in the next listing. Anything it routes to must still match the MCCF schema's names.

10. Events, cues and Loader playback

The Events Editor places cues on a playhead clock. The Composer writes them into scene.xml as EventCues, one Cue element per cue with track, target, label, t0 and dur attributes plus track-specific ones. The Loader reads EventCues > Cue and plays them against a scene clock that starts at zero when the scene loads.

Firing. fireScheduledEventCues sets one timer per cue at its t0, in seconds from scene start. It runs once per scene. The timers share one list with every other pending cue, so Stop and Reset cancel them together. The older named-trigger path (fireEventCuesForTrigger) is dormant: parsed cues no longer carry a trigger, so it matches nothing.

Track Handler What it does
camera _fireCameraEventCue Binds a baked viewpoint, or drives the free camera for a shot type
light, fog, bg _fireLightEventCue, _fireFogEventCue, _fireBgEventCue Changes a light, the fog, or the background
gesture, face _fireGestureEventCue, _fireFaceEventCue Plays a body clip, or an authored facial expression
behavior, animation _fireBehaviorEventCue, _fireAnimationEventCue Plays a cultivar behavior or an avatar animation clip
path, turn _firePathEventCue, _fireTurnEventCue Moves an agent or asset along a recorded path, or turns it
effect _fireEffectEventCue Triggers an effect on an effect target
movie _fireMovieVisibilityEventCue Shows or hides a movie screen
audio, midi _fireAudioEventCue, _fireMidiEventCue Plays a placed audio source, or a registered MIDI source

An unknown track logs a warning and does nothing.

Camera cues. Baked cameras are Viewpoint nodes in the X3D file, bound by name, and the Loader only binds them. Runtime cameras are a single free viewpoint that the Loader moves through the scripting interface. Ten static shot types are implemented: wide, medium, closeup, extreme_closeup, overhead, worms_eye, dutch, over_shoulder, profile and two_shot. The move shots dolly_in, dolly_out, pan, tilt, crane_up and orbit are implemented by interpolating those same values. A free-camera track shot is not implemented, and warns and skips. Agent orbit and agent track are the baked, parented versions.

Sources. Audio sources are read from AudioSources in the scene XML, not from the X3D proto, because the proto's ExternProto file failed to load. MIDI sources come from MidiSources with their per-track settings.

Dialogue lines are a separate system, read from Dialogue > Line and spoken through the same voice pipeline as waypoint dialogue. The scene-start, sensed (chained) and declared (fixed time) triggers are wired. Zone, touch and arc-complete triggers are parsed and round-trip, but by the code's own comment they are not fired yet.

11. DM codes and registry (proposal, not built)

Nothing in the code or schema carries a data module code today. Guide modules have stable ids only. This section is a proposal for review.

What a code needs. An S1000D data module code is built from: model identification code, system difference code, system code, subsystem and sub-subsystem codes, assembly code, disassembly code with variant, information code with variant, and item location code. For MCCF the model code would be fixed, and the system, subsystem and assembly codes would follow the system map in section 1. The information code separates descriptive modules from procedural ones.

Registry. One table in the CSDB repository, one row per module: stable id, DM code, title, issue number, issue date, status. The generator reads it to stamp each module's header (code, title and date on the left) and footer (provenance and page number).

Schema and code changes. The module schema gains a dmc element or attribute set. The generator refuses a module whose id is missing from the registry. Appendix B is regenerated from the schema as usual.

Decisions. Settled on 2026-10-26: chapter order drives the codes, and the code appears in the file name and in a module's header or footer. Codes are assigned last, as the final step before publishing, once Getting Started is written and all content is approved. Advice: the author is the sole code authority, since there is one author and one system. Assign codes by hand once and record them in the registry, which is the authority. Never reuse or renumber a code. Number in steps of 10 (system code from the Part, subsystem from the chapter, assembly code from the module's place in the chapter) so a module inserted later does not force renumbering. Information codes: use 040 (description) for explanatory modules, which is the usual single code for a small project, and one project-defined code for step-by-step modules such as Getting Started and the worked examples. S1000D allows project-specific information codes. Record the set in the registry. Leave the disassembly code at 00 with variant A, the information code variant at A, and the item location code at D (all locations), as other single-system projects do.

11a. Graphics register and ICNs (built in V5)

Pictures used by the PI lessons and the Guide are named and tracked as S1000D-style ICNs. This part of section 11 is built and in V5; the DM code registry above is still a proposal.

Name. ICN-MCCF-<tool>-<nnnn>-<issue>.<ext>, for example ICN-MCCF-CMP-0008-001.png. The name is an opaque, stable identifier. It carries no owner or module. The tool code is AMB (Ambient Composer), CMP (Scene Composer), LDR (X3D Loader), PI (Programmed Instruction), DSH (Dashboard), GDE (Guide) or GEN (General). The number is a plain sequence per tool code. The issue number goes up only when the picture itself changes. A version with numbered callouts burned in is a different picture, so it has its own issue (-002).

Register. registers/graphics_register.csv is the semantic record, one row per ICN: icn, issue, caption, tool, scene_or_data, used_in_dm, used_in_title, used_where, date_shot, shot_by, status (current, retake or superseded). The server writes it when a picture is added and keeps the previous copy as graphics_register.csv.bak. registers/callout_legend.csv lists the numbered controls of each callout picture for reference; the app does not read it.

Server (mccf_pi.py). GET /pi/media lists static/pi/media with each file's caption and the lessons that use it. POST /pi/media with a tool code and a caption stores the file under the next free ICN and adds the register row; if the register cannot be saved the file is not kept. GET /pi/graphics/tools and GET /pi/graphics/next?tool= support the add-a-picture dialog. POST /pi/graphics adds or edits one row, for a file already in the folder. GET /pi/graphics.csv downloads the register with the used-by columns filled in.

Used-by is derived, not stored. Each lesson frame names its picture in a Media element (file=). The server reads every lesson and works out which DM codes and titles use each picture, so the answer is always current. Uses in the Guide are not in the lessons, so they are recorded by hand in the register's used_in columns, and the download keeps them.

Callouts. A picture can have a sidecar <ICN>.callouts.json in static/pi/media: a list of numbered controls, each with a name, a description and its box as fractions of the picture. In the learner view the PI page draws the boxes over the picture. Clicking a box highlights the control's name in the step text; clicking the name in the text lights the box. The link is by matching the control's label in the text, so a step that calls a control by another name does not link. Pictures without a sidecar show no callouts.

Checks. The add-a-picture dialog and the server both refuse a missing file, an unaccepted file type, a file over 16 MB, no tool code and a caption under 8 characters, and say which.

Not done. Older pictures keep their old names until after the V5 release. The callout names for most panes come from the control labels and have not been edited by hand; the Actor Edit pane has. The Guide's Composer callout pictures (forms open, tables numbered to match) are not yet replaced by the new set, because the numbering differs.

12. Voice engine API: what MCCF could support later

Composition does not run against the voice engine's servers: authors render lines there by hand and bring the audio back. Someone building a more improvised, real-time experience would call the engine live. This section records what ElevenLabs offers, read from its documentation on 2026-10-25, so a later MCCF version can be designed for it. Nothing here is built.

Tags are not an enum. Eleven v3, v4 and v4 Turbo take natural-language tags in square brackets, placed where the delivery should change. The help page names [curious], [crying], [mischievously], [whispers], [shouts], [laughs], [clears throat] and [sighs] as examples. Anna's narration in The Garden of the Goddess uses 35 distinct tags, and almost all are free-form phrases such as [quietly, with profound conviction] and [with wonder]. A lexicon pack is therefore a vocabulary to draw from, never a validator.

Models (from the ElevenLabs overview page):

Model ID Role Audio tags Notes
eleven_v4 Most expressive Yes 90+ languages, 10,000 characters
eleven_v4_turbo Real time, about 100 ms Yes 90+ languages
eleven_v3 Dramatic delivery Yes 70+ languages, 5,000 characters, multi-speaker dialogue
eleven_flash_v2_5 Lowest latency, about 75 ms Not listed 32 languages
eleven_multilingual_v2 Stable long-form Not listed 29 languages

Endpoints that matter to MCCF

Endpoint What it gives Later MCCF use
POST /v1/text-to-speech/{voice_id} (and a stream form) One voice, inline tags, audio Render one Dialogue Line to an mp3
Text to speech with timestamps Audio plus per-character timing Save timing beside each mp3
POST /v1/text-to-dialogue (convert, stream, and timestamp forms) Up to 10 voices and 2,000 characters per request. Returns audio, a voice_segments list (voice, start and end seconds, character range, input index) and character alignment Render a whole scene's lines in one call, with correct turn-taking
Dialogue settings stability, similarity, clone_strength, seed, previous_text and future_text (100 characters each), previous and next request ids, pronunciation dictionaries (up to 3), audio_effects Continuity across lines, repeatable renders, per-scene pronunciation
wss .../stream-input Streaming audio chunks with alignment. Options: sync_alignment, auto_mode, inactivity_timeout (max 180 s), chunk_length_schedule, flush Real-time speech from a language model's token stream
Forced alignment (speech to text family) Aligns known text to existing audio Timing for audio made in a DAW, with no re-render
Sound effects, music, voice design, voice changer Generated sound and voices Optional sources for the audio library

Timing. The WebSocket alignment uses chars, charStartTimesMs and charDurationsMs, relative to each chunk. The REST forms use characters, character_start_times_seconds and character_end_times_seconds. A tag's character offset can be turned into a time, which would let a tag act as a timed control point on the emotional curve. Not yet checked: whether tags appear in the returned character list or are stripped. Test before designing on it.

Open questions in the documentation. The WebSocket page does not say which models it supports and defaults to eleven_multilingual_v2. An older cheat sheet lists audio tags for v3 only. Check both with a real call before a real-time design depends on them.

What MCCF could add, in order

  1. A voice-engine adapter beside the language-model adapters, with declared capabilities: tags, dialogue, streaming, alignment.

  2. A Render lines button that sends each line's ttsText to the engine through the MCCF server, saves the mp3 and its timing, and writes audioFile and audioSource into the line. The key stays on the server and never reaches the browser, which also removes the cross-origin exposure in IMPL-I07.

  3. Alignment-driven face and gesture cues, so lip sync and tag-timed expressions need no hand placement.

  4. Per-character voice settings: stability, similarity, style and speed driven by the cultivar's EBPS state, with a fixed seed so a render can be repeated.

  5. Real-time loop: language model, tag chosen from the live EBPS state by the decision tree (or a pack's own mapping), streamed speech, audio and alignment into the Loader. This needs a turbo or flash model and a measured latency budget.

  6. Pack fields for the engine: models supported, whether tags are free-form, placement, a group meaning (emotion, non-verbal, ambient), and an optional mapping from each tag to valence, arousal and engagement values, so a pack can drive suggestions instead of the fixed decision tree. An EmotionML mapping would sit in the same field.

Cautions. Character limits differ by model and endpoint. Logging can be switched off only on enterprise plans, so scene text goes to the provider by default. Use needs an account, a key and a plan. Voice cloning and use of a voice have their own terms.

Sources. ElevenLabs overview, audio tags help page, Text to Dialogue with timestamps, WebSocket stream-input, streaming with timestamps, third-party cheat sheet. A pasted Q and A was not used as a source: several of its details could not be confirmed.

13. Zones, scenes and playback modules

These modules were read from the files supplied on 26 October 2026. Each is a Flask blueprint or a plain library that mccf_api.py registers or imports. Findings are in the register (section 16).

Module What it does Notes
mccf_zones.py The zone model. A SemanticZone has a centre, a radius and an E, B, P, S bias. Pressure falls off smoothly from the centre to the edge. A zone also keeps a memory of past episodes that decays over hours and amplifies later pressure. SceneGraph holds zones, waypoints and paths and predicts the affective arc along a path. Eight presets. Pure computation, no file or network access. Preset names (intimate_alcove, forum_plaza, garden_path) differ from the zone types (intimate, forum, garden). Regulation changes are keyed by zone type.
mccf_zone_api.py The V2 REST layer over mccf_zones: /zone, /waypoint, /path, /scene/pressure, /sensor/spatial and an X3D zone export. The scene graph lives in memory and is empty after a restart. Findings IMPL-I18 and IMPL-I19.
mccf_zone_attractor.py V3. A zone gets its own channel vector from its Descriptor text, by matching words against a small vocabulary. An agent that stays inside a zone builds coherence with it, and the zone then pulls the agent's channels toward its own. Routes under /zones, plus ZoneSet XML import and export. It stores Zone elements in its own namespace (/zones/v3) and drops the Chorus child. See IMPL-I22 and IMPL-I23.
mccf_scene_wrapper.py V3. A SceneDefinition (zones and layout, reusable) and a SceneEpisode (one run, with its arc references). Routes under /scene/definition and /scene/episode. Uses the name EmotionalArc for a run reference, which is a third meaning of that word. Its GET /scene collides with the zone API (IMPL-I24).
mccf_scene_generate_api.py POST /scene/generate builds a whole X3D file from a SceneDefinition and cultivars, and writes static/mccf_scene.x3d. Also lists scenes and cultivars and receives /scene/x3d/upload. The older route to a scene file. The Composer's own export is the current route.
mccf_x3d_generator.py Called by the route above. Writes a self-contained X3D 4.0 file with a placeholder avatar PROTO, zone rings, sound nodes and a Script that polls /field every 200 ms. Fixed output name, so each run overwrites the last scene. The creation date in the header is fixed text.
mccf_versions_api.py Scene history and drafts. Saving a scene copies the old state into scenes/NAME/versions/NNNN first. Restore, promote and discard are all undoable. Writes are accepted from this machine only. Cleanest module in the set: atomic writes, a safe-name filter and a size-free history prune. The agent count was wrong after the rename; fixed in the patched copy (IMPL-I20).
mccf_playback.py Replays a recorded take (EmotionalArc file) through the field with no LLM. Walks scenes/NAME/arcs/TAKE. Several takes can play at once. Steps are timed or driven by the client. It overwrites each agent's channel weights as it plays (IMPL-I25).
mccf_chorus.py The Chorus. When an arc completes, it asks an LLM (stub, Ollama or OpenAI) for a short observation and shows it as an overlay. With a voice_actor it also builds a dialogue Line from that character's cultivar file. One Chorus per scene. The route /chorus/load looks in the wrong folder (IMPL-I26).

Zone XML in three forms. 14. Field, drift and sound modules

Module What it does Notes
mccf_couplers.py Seven coupler functions (Resonance, Damping, Inversion, Gated, Threshold, Delay, Integration) that return a change for the expressive channels. apply_coupler is the only entry point. Pure computation. The field tick in mccf_api.py gathers all changes before applying any.
mccf_drift.py Measures how far an agent's accumulated history pulls a response away from a fresh reading. Runs the same word-matching decomposition twice, with and without history, and reports the distance. Diagnostic only. It does not drive any control logic. Carries a second copy of the descriptor vocabulary.
mccf_collapse.py The S, P, G, M, U pipeline: schema limits, candidate scoring, honor filter, identity check, then one weighted random pick. Returns the chosen line and an XML record for the next stage. Built without a honor or trust object, so the honor stage does nothing (see below). Channel values for candidates are estimated from word lists, not from an LLM. Own zone table.
mccf_energy.py Scores candidate actions on valence, salience and coherence and ranks them with a temperature. Routes /energy/weights, /energy/evaluate, /energy/state. Adds random noise to every score, so two runs differ. The zone positions it uses for its salience bonus are fixed at z = 5 to 35.
mccf_neoriemannian.py Maps field state to triads and moves between them with the P, L and R operations. Returns frequencies for Web Audio. Plain computation. A GET to /neoriemannian/state steps every agent, so polling changes the state.
mccf_ambient_api.py The output bus: /ambient/sync returns lighting, music and voice settings from one field state. Also saves MIDI and Theme Workshop recipes into the media folder and holds the last arc mapping. The save routes check the file header, size, name pattern and that the request comes from this machine. They need nothing else. /ambient/sync and /lighting/* need mccf_lighting.py, which is not in the set.
mccf_hotHouse.py A stand-alone cultivar simulator with a dynamic trust field. mccf_api bridges core agents into it on request. Does not touch scenes or XML. Third copy of the zone biases.
mccf_honor_trust.py Honor penalties and trust propagation between agents. Deprecated for now, by decision of 26 October 2026. It is complete but not connected: mccf_api.py never imports it, never registers its routes, and builds the collapse pipeline without it. Keep the file and leave it unwired.

Obsolete module. mccf_lighting.py is retired (14 November 2026; the V3 spec had already dropped the Dashboard lighting panel). It is not needed and need not be found. mccf_ambient_api.py still imports it inside /ambient/sync, and the /lighting routes read what that call stores, so those routes fail with an import error until the lighting code is removed from the module. No V5 page calls them. Lighting is now set in the Composer (light sets, standard lights and per-actor lights) and written into the scene.
