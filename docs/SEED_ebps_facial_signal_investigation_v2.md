## What's new since the first seed doc

### Attempt #4: ROUTE-to-imported-node (untested in X_ITE, but the generator now works)

Community reference material (Google/Don Brutzman-sourced examples) confirmed a pattern never actually tried across attempts #1–#3: a **plain, XML-authored `ROUTE`** reaching directly into an imported node, resolved at scene-compile time — as opposed to `getNamedNode()` called from JavaScript at runtime, which is what every prior attempt used and which failed identically all three times.

New architecture, entirely different from anything tried before:
- **Anna's file needs no changes.** The 11 orphaned `HAnimDisplacer` EXPORT statements from attempt #2 are still there and are exactly what's needed.
- **A local `Transform`** (`FacialEBPSInputLocal_<suffix>`) lives directly in the *scene* file — never exported, never imported, so JS writes to it can never hit the cross-file failure mode at all, by construction.
- **A local `Script`** (`FacialEBPSMapper_<suffix>`), also never exported, receives the Transform's values via internal `ROUTE` and computes the same E/B/P/S→AU mapping as every prior attempt (unchanged: E→AU12+AU6, P→AU1+AU2+AU5, B inverted→AU4, S→AU26).
- **11 static `ROUTE`s**, authored directly in the scene file, carry the Script's outputs to the 11 imported displacers' `weight` fields. This is the actual, specific thing being tested — a `ROUTE` reaching an imported alias, which nothing before this attempted.

### This is now generated by Scene Composer itself, not hand-rolled

After being corrected (twice) for handing over hand-edited scene/avatar files that don't test the user's real workflow and risk clobbering manually-restored scene state, **all of attempt #4's structure was moved into `exportX3D()` in `mccf_scene_composer.html` itself**, keyed off the same `sn` (avatar suffix) variable the rest of the function already uses. Nothing about this requires touching the avatar file or the scene file by hand — load the real `scene.xml`, hit Export, and the generator produces it.

### A real bug was found and fixed in the generator — unrelated to the ROUTE question itself

First attempt to load the updated Composer threw browser errors: `SyntaxError: '' literal not terminated before end of script` and `SyntaxError: invalid escape sequence`. **This had nothing to do with the exported X3D or the ROUTE architecture** — it was Composer's *own* HTML breaking. The generator code built a JS string containing the literal text `</Script>` (meant as X3D output text). A browser's HTML parser doesn't understand JavaScript — it scans raw bytes inside a `<script>` tag for the literal sequence `</script` (case-insensitive) to know where the script block ends, with zero awareness of JS string literals. That literal string prematurely closed Composer's own `<script>` tag, corrupting everything after it in the file.

Fixed with the standard technique: `<\/Script>` instead of `</Script>` — identical string value at runtime, but the raw source bytes no longer match the HTML parser's trigger sequence. **Verified properly this time**: extracted the actual generated block from the whole file (not a hand-picked snippet), confirmed it's complete, confirmed it passes syntax check as a whole, confirmed the dangerous sequence is gone and the escaped version is present exactly once. Confirmed by the user: Composer now loads correctly.

**Lesson for anyone touching this generator code again**: any time generated output text contains `</script`-like sequences (for any tag, case-insensitive), it needs this same escape treatment, or it will silently corrupt the *tool's own* HTML the moment it's loaded — `node --check` on the generator's own JS syntax will not catch this class of bug, because Node doesn't do HTML parsing at all. Verify by checking the *rendered/loaded* file, not just the JS that produces it.

## What's still completely untested

1. **Whether exporting the user's real, restored `scene.xml` through the fixed Composer produces a correctly-structured X3D file** — the generator code is verified correct in isolation, but no real export has been run through it yet.
2. **Whether the resulting X3D file actually loads cleanly in X_ITE** — same class of check as every prior attempt (valid XML, all 11 imports present, the local Transform/Script present, all 11 cross-boundary ROUTEs present).
3. **Whether the ROUTE-to-imported-node pattern itself actually works in this X_ITE version** — this is the entire point of attempt #4, and it remains completely unknown. If a plain XML-authored `ROUTE` also fails to reach an imported alias, that's new, stronger, stranger information — worth taking directly to the W3DC working group as-is, since it would rule out both mechanisms X3D offers for crossing this boundary (SAI lookup and ROUTE), not just one.

**The actual test, once a real export exists**: watch Anna's face during a scene run with a real E swing, or manually in the browser console:
```js
canvas.browser.currentScene.getNamedNode('FacialEBPSInputLocal_Anna').translation = new X3D.SFVec3f(0.9, 0.25, 0.25);
```
This specific call is guaranteed to succeed regardless of the ROUTE question — it's a local node, never crosses any boundary. What answers the real question is **whether her face visibly moves afterward**, which depends entirely on whether the 11 static ROUTEs into the imported displacers actually work.
